`POST /v1/chat/completions` accepts the standard OpenAI request body and returns the standard `chat.completion` object. Any OpenAI client works against it unchanged.

```bash
curl -sS "$KIBBU_BASE_URL/chat/completions" \
  -H "Authorization: Bearer $KIBBU_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{
    "model": "'"$KIBBU_MODEL"'",
    "messages": [{ "role": "user", "content": "Say hello." }]
  }'
```

## Request

<ParamField body="model" type="string" required>
  A model id from `GET /v1/models`. May carry a `:adapter` suffix to select a LoRA adapter — see [Kibbu extensions](/api/extensions).
</ParamField>

<ParamField body="messages" type="array" required>
  The conversation, in OpenAI's `{ role, content }` shape.
</ParamField>

<ParamField body="stream" default="false" type="boolean">
  Stream `chat.completion.chunk` objects over Server-Sent Events, terminated by `data: [DONE]`.
</ParamField>

<ParamField body="tools" type="array">
  Tool definitions in OpenAI's shape. Kibbu never hands `tools` to a model that has no template for them and hopes for the best. If cloud fallback is configured for that model the request is routed there; if it can only be served locally you get `400 model_does_not_support_tools`.
</ParamField>

<ParamField body="response_format" type="object">
  Structured output. Malformed or unsupported shapes return `400 response_format_invalid`.
</ParamField>

<ParamField body="max_completion_tokens" type="integer">
  Must be a positive integer. `0` or a negative value returns `400 invalid_max_completion_tokens`.
</ParamField>

<ParamField body="n" default="1" type="integer">
  Most models serve a single completion per call and return `400 n_not_supported` for `n > 1`.
</ParamField>

Kibbu also accepts several optional additive fields — `tier`, `lora_id`, `reasoning_effort` and others. A client that never sets them sees byte-identical behaviour. They are documented in [Kibbu extensions](/api/extensions).

## Streaming

```bash
curl -sS -N "$KIBBU_BASE_URL/chat/completions" \
  -H "Authorization: Bearer $KIBBU_API_KEY" \
  -H "Content-Type: application/json" \
  -d '{"model":"'"$KIBBU_MODEL"'","stream":true,"messages":[{"role":"user","content":"Count to five."}]}'
```

The wire format is the OpenAI SSE format, including the `data: [DONE]` terminator, so streaming clients need no changes.

## When a stream is interrupted

Machines are laptops. They get closed, unplugged and reclaimed by their owners mid-answer. What reaches you depends on whether any content had already been sent.

| What happened | What arrives | What you do |
| --- | --- | --- |
| It failed before the first token | An ordinary HTTP error envelope. The stream never started. | Branch on `code`. |
| The machine was lost before the first token | Nothing. Kibbu holds the response and restarts on the next rung. | Nothing. The answer is whole. |
| The machine was lost after the first token | A `kibbu_failover_required` frame, then `data: [DONE]`. | Reissue the request if `retry` is true. |
| It failed after the first token | A `data: {"error":{…}}` frame, then `data: [DONE]`. | Branch on `code`. Do not treat it as a short answer. |
| You closed the connection | Nothing. A client cancel is not a server fault. | Nothing. |

<Warning>
  **`data: [DONE]` is always emitted, including after a failure.** Reaching the terminator does not mean the answer is complete — the signal is the frame immediately before it.
</Warning>

### The failover frame

Once a single content token has reached you, Kibbu cannot quietly restart the request elsewhere: the partial answer is already on the wire, and a fresh completion would contradict it. So it names the problem instead of dropping the connection.

```
data: {"kibbu_failover_required":{"reason":"owner_returned","retry":true,"retry_after_ms":0}}

data: [DONE]
```

| Field | Meaning |
| --- | --- |
| `reason` | `node_unavailable` — the machine died or went unreachable. `owner_returned` — its owner came back and Kibbu yielded. `stream_interrupted` — anything else. |
| `retry` | Whether reissuing is worth it. `false` means surface the failure now. |
| `retry_after_ms` | How long to wait first. `0` means immediately. |

A stock OpenAI client does not know this frame. It skips the unrecognised object, reaches `[DONE]`, and hands you a **truncated answer that looks complete**. If you stream to users, read the raw lines yourself:

```python
import json, httpx

with httpx.stream("POST", f"{BASE_URL}/chat/completions", headers=HEADERS, json=body) as r:
    for line in r.iter_lines():
        if not line.startswith("data: "):
            continue
        payload = line[6:]
        if payload == "[DONE]":
            break
        frame = json.loads(payload)
        if "kibbu_failover_required" in frame:
            signal = frame["kibbu_failover_required"]
            if signal["retry"]:
                ...  # wait signal["retry_after_ms"], then reissue
        elif "error" in frame:
            raise RuntimeError(frame["error"]["code"])
        else:
            ...  # an ordinary chat.completion.chunk
```

## Response headers worth reading

| Header | Meaning |
| --- | --- |
| `X-Kibbu-Serve-Path` | Which rung actually served you: `edge` for your own machines, `cloud` for a provider. Absent when Kibbu cannot say. The only way to tell whether an `upstream_error` came from your hardware or someone else's. |
| `X-Kibbu-Slow-Serve` | The request was served on hardware below the interactive speed floor, because that was better than refusing. Expect a slow answer. |
| `X-Kibbu-Budget-Warning` | Your organization has passed a percentage of its spend budget. The request was still served. |
| `Retry-After` | On `429` and most `503`s, how long to wait. |
| `x-ratelimit-*` | Remaining requests and tokens under the current caps. |

## Errors specific to this endpoint

| HTTP | `code` | Meaning |
| --- | --- | --- |
| `400` | `context_length_exceeded` | Prompt plus completion exceed the model's context window. |
| `400` | `model_kind_mismatch` | An embedding model was addressed at a chat endpoint. |
| `400` | `model_does_not_support_tools` | The model has no tool template and no cloud rung to divert to. |
| `400` | `invalid_tier` | Unknown `tier`. Use `reserved`, `interactive`, `batch` or `idle`. |
| `404` | `model_not_found` | The id is not enabled for your organization. |
| `413` | `request_too_large` | The body exceeds the inference body cap (10 MiB by default). |
| `503` | `model_warming_up` | The machine is still loading the model. Retry after 30s. |
| `503` | `fleet_busy` | Every rung was tried and none could serve. Retry shortly. |

The full list is in [Error codes](/reference/errors).
